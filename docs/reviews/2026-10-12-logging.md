# Logging completeness review (2026-10-12)

**Scope:** what the harness does but never records, what it records but nothing reads.
Sources: `docs/log-grammar.md`, `skills/hooks/` (telemetry writers), `scripts/offensive.py`,
`watcher.py`, `pmonitor.py`, `curator.py`, `eval_metrics.py`, `session/*` rotation, live
evidence from the active engagement under `targets/` (2549 events, 2026-10-06 to 10-12).

## Envelope

Top-3 by cost of the unanswerable question:

1. **`.metrics.json` corrupts under concurrency and wipes itself** (D1): 8 "baseline
   reset" events, two in the same microsecond; `started_at` reads Oct 12 (box began
   Oct 6), `spend_usd` and pre-Oct-12 transcripts gone; the `ZT_MAX_ENG_USD` cap flies
   blind. Cause: three bare `open(w)` writes in `tool-telemetry.py`.
2. **Per-lane token spend is never captured** (D2): no SubagentStop/Notification hook;
   the `| usage Nt/Ns` lane cell is manual-only, its parser has zero production
   callers. "Which lane burned the budget?" unanswerable.
3. **The framework audit is 6 days stale** (D3): `session/log.md` holds one line
   (2026-10-06), `hot.md` untouched since Oct 6, while Oct 10-12 hermes-port work
   landed. Nothing enforces pause-work.

## Defects (ranked)

### D1. `.metrics.json` concurrent-write corruption silently wipes spend, transcripts, start time
- **Evidence:** 8 `kind:"telemetry" error:".metrics.json unparseable - baseline reset"`
  events in the engagement's `.events.jsonl`; two resets at `12:21:46.975681` /
  `.975684` (two hook processes colliding). Current `.metrics.json`: `started_at`
  2026-10-12T12:23 vs first event 2026-10-06T06:48; no `spend_usd` key at all;
  `transcripts` reduced to the one Oct 12 session. `tool-telemetry.py` writes the file
  non-atomically in three places (`_spend_update` ~L145, `_mentor_check` ~L249,
  `_turn_bytes` ~L309) while `_telemetry._save` (tmp + `os.replace`) sits unused beside them.
- **Consequence:** "What did this engagement cost and how long did it run?" is wrong or
  unanswerable; `status.py` `spend:` shows a silent `$0.00`; `ZT_MAX_ENG_USD` never
  triggers; `eval_metrics` token attribution drops every wiped transcript (the Oct 6
  session's ~1100 events have no token column anymore).
- **Fix:** route the three write sites through `_telemetry._save`. One-line change each.
- **Effort:** S.

### D2. Lane token spend never auto-captured; usage-cell parser is dead code
- **Evidence:** `.zcode/config.json` registers SessionStart/UserPromptSubmit/PreToolUse/
  PostToolUse/Stop/PreCompact only; subagent completion notifications (which carry
  usage) hit no hook. `lane_validate.usages_from_text` ("for spend accounting") is
  called only by `tests/test_lane_validate.py`. Zero `| usage` cells in 115 lines of
  the engagement's `log.md` (115 lines sampled).
- **Consequence:** "Which lane consumed the tokens / did cheap-tier delegation actually
  save money?" unanswerable; brain-mode lane comparison is vibes.
- **Fix:** a SubagentStop (or PostToolUse-on-Task) hook appending
  `kind:"lane_usage" {lane, in, out, model}` from the notification; then wire
  `usages_from_text` into `eval_metrics`.
- **Effort:** M.

### D3. Framework audit stores stale: `session/log.md` has one line (Oct 6), `hot.md` untouched since Oct 6
- **Evidence:** `session/log.md` = 1 line, dated 2026-10-06; `session/hot.md` mtime
  Oct 6 11:26; repo commits Oct 10-12 (hermes waves, memory gap fix) produced no
  session-store writes. AGENTS.md requires updates "after every ingest, lint pass";
  nothing checks or nudges it. The Stop hook (`close-out.py`) only fires on SOLVED
  engagements.
- **Consequence:** "What harness work happened this week and why?" has no record; a new
  session boots with a 6-day-old hot cache; the pause-work forgetting gap commit
  b213309 addressed memory, not the store.
- **Fix:** extend the Stop hook: if `session/hot.md` mtime is >24h old and the branch
  has commits newer than that, one nudge line. Plus the existing memory close-out sweep.
- **Effort:** S.

### D4. Driver decision trail is print-only (`next` banners), not persisted as events
- **Evidence:** `cmd_next` persists `last_move`/`pass`/`serve_count`/`terminal_count`
  (good) but WALL-BREAK fires, RE-SERVE x2/x3 banners, TERMINAL 3x, PARALLEL posture,
  G4 zombie-row suppression, and `plan` (explicitly "writes nothing") leave only
  side-effects in `.offensive.json`. No `kind:"driver"` events exist in any
  `.events.jsonl`. `autonomy` is the one driver command that does write an event.
- **Consequence:** "How many times did the driver intervene (wall-break, re-serve
  warnings) before the operator saw drift?" unanswerable post-hoc; postmortems cannot
  distinguish "driver never warned" from "warning scrolled past".
- **Fix:** `_telemetry.log_event("driver", action=...)` at each banner branch in
  `cmd_next` (it already links `_events` for G2, so the dependency exists).
- **Effort:** S.

### D5. Drift signals (505 recorded) are never re-surfaced in-session, and 77% are mentor noise
- **Evidence:** drift sources in the sample engagement: mentor 390, lane-guard 70,
  context-low 19, close-out 16, drift-guard 8, sleep-guard 3. Readers of
  `kind:"drift"`: `eval_metrics.py` only (close-out). `engagement-init.py` SessionStart
  injects board/lanes/OOB HITs, not recent guard signals; after a compaction the
  advisory text is gone from context and never returns.
- **Consequence:** "What did the guards try to tell me that I ignored?" needs a manual
  file read; close-out `drift_count: 505` buries the ~100 real signals (denies,
  context-low) under mentor repeats.
- **Fix:** one SessionStart line ("guard signals since last start: N; top: lane-guard
  denies x70") from the events tail; log mentor as its own `kind:"mentor"` so
  `drift_count` means enforcement again.
- **Effort:** S.

### D6. `autonomy_change` event violates the schema (`event` key, not `kind`)
- **Evidence:** `offensive.py` `cmd_autonomy` writes `{"ts", "event":
  "autonomy_change", ...}` directly to `.events.jsonl` instead of via `_telemetry`
  (`kind`). The one such row in the sample is the file's only `kind: None` line;
  every consumer (`eval_metrics`, `curator`, `_skill_fired`) filters on `kind`.
- **Consequence:** "When did the autonomy envelope change and why?" is invisible to
  every kind-based reader; schema consumers see a malformed row.
- **Fix:** `_telemetry.log_event("driver", event="autonomy_change", ...)`, or add
  `"kind": "driver"` to the dict.
- **Effort:** S.

### D7. `.compact-log.jsonl` written by PreCompact, read by nothing
- **Evidence:** `pre-compact.sh` appends one ledger record per compaction (ts, pass,
  asset_cursor, dry_streak, board counts) explicitly "correlating compactions against
  driver state ... doom loop becomes visible". Grep across `scripts/`, `skills/`,
  `docs/`: the only file referencing it is `pre-compact.sh` itself. Not surfaced by
  `status.py`, `offensive-doctor`, `eng-postmortem`, or `eng-close`.
- **Consequence:** the compaction-doom-loop correlation its own comment promises never
  runs mechanically; "did compaction restart the same move?" requires a hand analysis.
- **Fix:** `offensive-doctor` (or status) prints the last 3 ledger rows and flags a
  repeated `asset_cursor` + `last_row` pair.
- **Effort:** S.

### D8. The `log.md` audit-line convention has no mechanical writer, and its `<TS>` is date-only
- **Evidence:** `docs/log-grammar.md` says "Hook telemetry writers use this shape
  `(<TS> | category | action | result | detail)` for their human-readable log.md
  lines"; no hook writes any such line (the only scripted writer is `pmonitor.py`'s
  `- ts | pmon | ...`). the sample engagement's `log.md`: 20 audit lines against 1807 tool
  events; every audit `<TS>` is `2026-10-12` with no time-of-day while lane lines
  carry `@09:12`, so intra-day ordering between the two cannot be reconstructed.
- **Consequence:** "Rebuild Tuesday's timeline" from the human log is impossible; the
  walkthrough leans on board state and memory instead of an audit.
- **Fix:** pick one side: either amend the grammar doc to "agents write these, hooks
  stay JSONL-only" and add `HH:MM` to the `<TS>` convention, or have `tool-telemetry`
  mirror hook `deny`/`ask` actions into `log.md` audit lines.
- **Effort:** S (doc) / M (mirror).

### D9. `write-guard` asks and operator decisions leave no record at all
- **Evidence:** `write-guard.py` (PreToolUse Write/Edit onto binaries, `ask`) contains
  zero `_telemetry` calls; `scope-guard` RoE pre-approvals do log
  (`drift "roe tooling pre-approved by operator"`), so the gap is inconsistent, not a
  design choice. The grammar's `hitl ask`/`hitl decided` tokens have no writer
  anywhere in the tree.
- **Consequence:** "Which binary overwrites / RoE escalations did the operator approve,
  and when?" unanswerable; an approved destructive overwrite is indistinguishable from
  an unguarded one in every record.
- **Fix:** one `log_event("hook", hook="write-guard", action="ask", detail=kind)` in
  `write-guard.py`; emit `hitl decided` lines where the harness reports the operator
  choice back.
- **Effort:** S.

### D10. `watcher.py` marks digests delivered in DRY mode, and it is scheduled by nothing
- **Evidence:** `tick()` appends pending ids to `.watcher-state.json sent` BEFORE the
  telegram env check; with no env vars the entries print to stdout and are still
  claimed, so one accidental dry `--once` permanently suppresses those digests for any
  later configured run. Docstring: "DEFAULT OFF: nothing schedules it"; no hook or cron
  references `watcher.py`.
- **Consequence:** `-> VERIFIED`, `OOB HIT`, `FIND` lines (the grammar events it exists
  to digest) have a reader that is never running and a claim ledger that can silently
  eat the queue; "did the operator ever see the finding ping?" unanswerable.
- **Fix:** claim only on successful send (keep a separate `dry_seen` list for dry
  ticks); wire `--once` into SessionStart or document the cron line as required setup.
- **Effort:** S.

## Well-logged things (keep as-is)

1. **Per-tool telemetry events** (`tool-telemetry.py`): every call lands with `ts`,
   tool, invoked binaries (names only, leak-safe), skill name for `Skill`, wiki-page
   path for wiki reads, and `out_bytes`; 1807/1807 rows carry timestamps and binary
   attribution, which is what makes `eval_metrics` histograms and G2 skill-gating work.
2. **The compaction survival chain**: `last_move` persisted in `.offensive.json` on
   every serve, PreCompact MUSTSURVIVE block (open lanes, board count) in the
   summarizer instruction stream, `.compact-log.jsonl` ledger, and SessionStart(compact)
   verbatim re-injection; the served move demonstrably survives compaction.
3. **Enforcement audit machine-side**: scope-guard/lane-guard/sleep-guard/drift-guard
   write `kind:"hook"` (action) plus `kind:"drift"` (source + one-line reason) for every
   deny/advise, and drift-guard additionally logs `kind:"advice" action:"complied"`
   when advice was heeded, giving a worked-vs-ignored denominator no other component has.
   (Bonus: `_ckpt` shadow-git commits after every driver mutation give byte-level board
   history.)

## Priority order if only three get fixed

D1 (data loss now, S), D2 (the only spend dimension missing, M), D5 (surface what is
already recorded, S). D3-D4, D6-D10 are S-effort and can ride the next harness pass.
